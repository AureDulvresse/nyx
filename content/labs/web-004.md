## Scénario

`filemanager.lab` (10.10.0.10) héberge une application de gestion documentaire interne qui permet d'afficher des fichiers via un paramètre d'URL. Personne n'a jamais vérifié ce que ce paramètre acceptait vraiment. Ta mission : transformer cette inclusion de fichier locale en exécution de commandes sur le serveur.

## Objectifs

1. Confirmer une inclusion de fichier local (LFI) exploitable via le paramètre `page`
2. Utiliser une technique de log poisoning pour injecter du code PHP dans un fichier journal accessible
3. Inclure ce journal empoisonné pour obtenir l'exécution de commandes (RCE)

## Indices

- Le paramètre `page` accepte des chemins relatifs (`../../../`) sans filtrage sérieux — commence par lire un fichier système classique comme `/etc/passwd` pour confirmer la faille.
- Le serveur web journalise le User-Agent de chaque requête HTTP dans un fichier accessible depuis l'inclusion — un User-Agent contenant du code PHP peut donc s'y retrouver injecté.
- Une fois le journal empoisonné, inclus-le via le paramètre `page` : le code PHP injecté s'exécute alors dans le contexte du serveur.

<WarningCallout>
La LFI et le log poisoning sont deux techniques distinctes qui, combinées, deviennent bien plus dangereuses qu'une simple lecture de fichier — c'est exactement ce genre de chaînage que l'audit doit anticiper.
</WarningCallout>

<TipCallout>
Ce lab prolonge directement les chapitres sur les inclusions de fichiers du cours Sécurité Web (OWASP) — relis la section sur le log poisoning si l'étape d'injection ne fonctionne pas du premier coup.
</TipCallout>
